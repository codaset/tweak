# Chrome extension APIs for the v1 design

Ticket: codaset/tweak#8. Researched 2026-11-25 against developer.chrome.com, Chromium source (`main`), and experiments in Chrome for Testing 158.0.8127.36 (headless, unpacked MV3 test extension, macOS arm64).

Evidence labels: **[verified-exp]** observed in my experiment; **[verified-src]** read in Chromium source; **[verified-doc]** stated in Chrome's docs; **[inferred]** reasoned from the above, not observed.

## Answer

1. **Runtime registration works as the design wants.** `chrome.scripting.registerContentScripts` with `world: "MAIN"`, `runAt: "document_start"` ran before any page script and before `<body>` existed. The same call succeeds with no host permission, but the script then does not inject until permission exists for those origins. Register at runtime and request the permission separately. [verified-exp]
2. **Registered scripts do not survive an extension install or update.** Chromium wipes the stored registrations on install and update (and I saw them gone after relaunching an unpacked extension). The service worker must re-register from the bridge's claim list on `runtime.onInstalled`, `onStartup`, and each worker start (diff against `getRegisteredContentScripts`). Ordinary browser restarts persist them by default (`persistAcrossSessions` defaults true), though I could not test that with an unpacked extension. This matters because the design tells people to reload an older unpacked extension. [verified-src, partly verified-exp]
3. **Optional host permissions need a real user gesture; the bridge cannot trigger them.** `permissions.request` fails with "This function must be called during a user gesture" from the service worker and from an extension page with no click. A click in an extension page (side panel, popup) works, and the gesture also carries through `runtime.sendMessage` to the service worker. A claim learned from the bridge can therefore only raise the grey `!` badge and offer an "Allow" button in the side panel. It cannot prompt by itself. [verified-exp for the failures and the page click; the SW path is pending-not-rejected, see below]
4. **`chrome.sidePanel.open` needs a gesture, and the gesture is short-lived inside the service worker.** The docs list action click, keyboard command, context menu click, and a gesture on an extension page or content script. In my test a content-script click relayed by message opened it; the same call deferred 1.5 s inside the worker was refused. Call `open()` straight from the `onCommand` / `contextMenus.onClicked` handler with no awaits before it. [verified-doc + verified-exp]
5. **Per-tab badges work but do not reset on navigation.** `setBadgeText({tabId})` is scoped to the tab, and the value survived reload, same-origin navigation, `pushState` and a cross-origin navigation. The extension must clear or recompute it on `tabs.onUpdated`/claim changes. Keep text to about four characters. [verified-exp, verified-doc]
6. **`captureVisibleTab` does not work with per-domain host grants.** It needs `activeTab` on that tab, or the literal `<all_urls>` pattern. Granting `*://*.test/*` or even `*://*/*` is not enough. Limit: 2 calls per second (the extra call rejects). The result is the viewport only, at device pixels (2400x2674 for a 1200x1337 viewport at DPR 2), and it includes cross-origin iframes and your own overlay. [verified-src + verified-exp]
7. **The conflict with the design is the screenshot.** Pick mode by ⌥-click and the Send button are not `activeTab` invocations, so v1 must either request optional `<all_urls>` once (one scary prompt, which also makes per-domain prompts unnecessary) or fall back to `activeTab` grants only when the user starts from the toolbar button, ⌥⇧ shortcut or context menu. See "Awkward for the design".

## 1. Runtime content-script registration

Sources: [scripting reference](https://developer.chrome.com/docs/extensions/reference/api/scripting), [content scripts guide](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), Chromium `extensions/browser/api/scripting/scripting_api.cc`, `extensions/browser/user_script_manager.cc`, `extensions/browser/state_store.cc`.

- Permissions: manifest needs `"scripting"` plus host permissions. The docs say "declare the scripting permission in the manifest plus the host permissions for the pages to inject scripts into". [verified-doc]
- Fields: `world` (`ISOLATED` default, `MAIN`), `runAt` (`document_start` allowed), `persistAcrossSessions` (default true), `matches` (required), `allFrames` (default false), `matchOriginAsFallback` (Chrome 119+). Registration is atomic: a bad entry or duplicate id registers nothing. [verified-doc]
- **MAIN + document_start (experiment).** Registered `{world:"MAIN", runAt:"document_start", matches:["http://localhost/*"], js:["main.js"]}` from the service worker. On `http://localhost:5201/` (a port was present, pattern had none) `main.js` ran at about 5.9 ms with `document.body` null, and an inline script in the page `<head>` saw its effect (`__sawMain` 1) while the script's own check of a page-defined variable was `undefined`, so it ran before page scripts. [verified-exp]
- **Registering without permission.** With only `optional_host_permissions` declared and nothing granted for `127.0.0.1` or `foo.test`, `registerContentScripts` returned success and `getRegisteredContentScripts` listed them. Loading `http://127.0.0.1:5201/` then showed no injection; `localhost` (granted) did inject. So the match pattern is stored independently of access and applies only where the extension has access. [verified-exp] The docs are silent on this.
- **Matching origins learned at runtime.** `matches` takes any valid match pattern, built from the claim at runtime. A pattern without a port matched port 5201. Patterns may carry a path, so `https://ernie.localhost/admin/*` maps directly. [verified-exp for portless; verified-doc for the rest of the grammar at [match patterns](https://developer.chrome.com/docs/extensions/develop/concepts/match-patterns): host wildcard only as leading `*.`, port optional and a wildcard when omitted, scheme `http|https|*|file`]
- `updateContentScripts` changes only the fields passed; unknown ids reject the whole call; `getRegisteredContentScripts({ids})` filters. No documented cap on the number of scripts. [verified-doc]
- **Persistence.** `persistAcrossSessions` defaults true, and the loader reads stored scripts back when the extension loads (`ExtensionUserScriptLoader::AddScriptsForExtensionLoad` -> `GetDynamicScripts`). But `StateStore::OnExtensionWillBeInstalled` calls `RemoveKeysForExtension`, and `kRegisteredScriptsStorageKey` is registered with the store (`user_script_manager.cc`), so registrations are deleted on every install, including updates (`is_update`). In my runs, relaunching the browser with the unpacked extension (which reinstalls it) left `getRegisteredContentScripts()` empty, with a script registered with default persistence beforehand. I could not test a true cold restart with an installed extension. [verified-src; unpacked relaunch verified-exp; normal-restart persistence inferred]
- **Already-open tabs.** Registration affects later navigations. The docs do not say; I did not test `scripting.executeScript` on existing tabs. After a claim, tabs already on the page need a reload or an explicit `executeScript` (host permission required). [inferred]

## 2. Optional host permissions for new dev domains

Sources: [permissions reference](https://developer.chrome.com/docs/extensions/reference/api/permissions), [declare permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions), [match patterns](https://developer.chrome.com/docs/extensions/develop/concepts/match-patterns).

- Declare `"optional_host_permissions": ["*://*/*"]` (or `<all_urls>`, see section 5) so any origin can be requested at runtime; the docs say this lets you request any origin "as long as it has a matching scheme", and you can request subsets. Paths on origin patterns are ignored. `permissions.contains({origins})` checks; `onAdded`/`onRemoved` fire on change. [verified-doc]
- **Gesture.** The docs: "Permissions must be requested from inside a user gesture, like a button's click handler." They do not say which contexts qualify. Observed:
  - Service worker, no gesture: rejected, "This function must be called during a user gesture". [verified-exp]
  - Extension page, no gesture (script eval): same rejection. [verified-exp]
  - Extension page, real click (trusted click through CDP): no rejection; the promise stays pending because headless Chrome has no permission dialog UI to accept. I could not observe a grant. [verified-exp; grant outcome not observed]
  - Click in an extension page, then `runtime.sendMessage` to the worker, which calls `permissions.request`: also pending rather than rejected, so the gesture crosses the message. [verified-exp, with the same caveat]
- So from the surfaces: side panel and popup (extension pages) can call it directly from a click. The worker can call it from `action.onClicked`, `commands.onCommand`, `contextMenus.onClicked` (all gestures per the docs, [verified-doc] for sidePanel; for permissions this is [inferred]). Content scripts cannot call `chrome.permissions`; relay by message from a real click. The bridge's claim event never counts as a gesture.
- Patterns like `*://*.test/*`, `*://lvh.me/*`, `*://*.localhost/*` are all valid grammar (leading `*.` plus host). The docs do not discuss TLD-only wildcards. I could not exercise the prompt text. [verified-doc grammar; prompt behaviour inferred]
- Ports: the docs say patterns match all ports unless one is given, and my portless registration matched `:5201`. Whether `permissions.request` accepts an explicit port was not tested; build requests from scheme and host only. [verified-exp / inferred]

## 3. `chrome.sidePanel`

Source: [sidePanel reference](https://developer.chrome.com/docs/extensions/reference/api/sidePanel), [commands](https://developer.chrome.com/docs/extensions/reference/api/commands), [contextMenus](https://developer.chrome.com/docs/extensions/reference/api/contextMenus), [activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab).

- Needs `"sidePanel"` permission; `open()` is Chrome 116+, `close()`/`onOpened` 141+, `onClosed` 142+. `open({tabId})` or `open({windowId})`, at least one required (error "At least one of `tabId` and `windowId` must be provided"). A tab with its own per-tab panel opens only that panel. [verified-doc, error text verified-exp]
- Gesture rule (docs): "This may only be called in response to a user action", and the listed actions are an action click, a keyboard shortcut (commands), a context menu click, and a user gesture on an extension page or content script. [verified-doc]
- Observed: from the worker without a gesture: "`sidePanel.open()` may only be called in response to a user gesture." From a real click in an extension page, directly or relayed to the worker: opened. From a real click on a web page, relayed from a content script through `runtime.sendMessage`: opened (first relay), opened again by a second relay 1.5 s after the click, but a `setTimeout(1500)` inside the worker before `open()` was refused. So the grant is tied to handling that message, not to the worker afterwards. [verified-exp] I did not get a conclusive result for short awaits (storage, fetch); keep `open()` synchronous in the handler. [not tested]
- **Action context menu and keyboard command:** `contextMenus` item with `contexts: ["action"]` (the docs: "Applies to the context menu of the extension's action (its toolbar icon)") and `commands.onCommand` are both on the docs' list, so `sidePanel.open({tabId: tab.id})` called first in those handlers is allowed. I could not drive a native menu or a real keystroke in headless Chrome. [verified-doc, not exercised]
- Create context menu items in `runtime.onInstalled` (docs example); the contextMenus page itself says nothing about worker restarts. [verified-doc]
- `sidePanel.setPanelBehavior({openPanelOnActionClick})` defaults false; leave it false so `action.onClicked` can toggle pick mode. `action.onClicked` does not fire if the action has a popup. [verified-doc]
- Commands: shortcuts must include Ctrl or Alt; Ctrl+Alt is forbidden; at most four suggested keys; users can rebind at `chrome://extensions/shortcuts`; on macOS `Alt` is Option. The design's ⌥⇧C, ⌥⇧H, ⌥⇧N (three) fit. A key another extension already holds will not register. [verified-doc]

## 4. Per-tab action badges

Source: [action reference](https://developer.chrome.com/docs/extensions/reference/api/action).

- `setBadgeText`, `setBadgeBackgroundColor`, `setBadgeTextColor` take `tabId`: "Limits the change to when a particular tab is selected. Automatically resets when the tab is closed." Tab-specific values beat the global one. Text: "we recommend four or fewer characters". [verified-doc]
- Observed: with global text cleared, setting `tabId` A to "7" gave A "7", another tab "" and global "". After a same-origin navigation, `history.pushState`, a reload, and a navigation to `127.0.0.1` (cross-origin) the value on A was unchanged each time. [verified-exp] The docs are silent on navigation; the old MV2 reset-on-navigation does not apply.
- Consequence: a grey `!` set for an unclaimed page stays after the tab navigates to a claimed page. Recompute on `tabs.onUpdated` (status `loading`) and on every claim change, for every tab. Reading `tab.url` for that needs a host permission or `tabs`; with `<all_urls>` or granted dev domains that is available, otherwise unclaimed-vs-unknown pages can't be told apart. [verified-doc for `tabs` url gating: https://developer.chrome.com/docs/extensions/reference/api/tabs; inferred for the consequence]
- Per-tab count and colour (blue/amber/purple) are supported by tab-scoped `setBadgeBackgroundColor`. [verified-doc]

## 5. `chrome.tabs.captureVisibleTab`

Sources: [tabs reference](https://developer.chrome.com/docs/extensions/reference/api/tabs), Chromium `extensions/common/permissions/permissions_data.cc` (`CanCaptureVisiblePage`), `extensions/common/url_pattern.cc`.

- Signature `captureVisibleTab(windowId?, options?)`; captures "the visible area of the currently active tab in the specified window". Permission: `<all_urls>` or `activeTab`. [verified-doc]
- **Per-domain grants are not enough.** In the source, access needs `has_active_tab` (tab-specific `activeTab` grant) or `has_all_urls`, which is true only when an explicit host permission's `match_all_urls()` is true. `URLPattern::SetMatchAllURLs(true)` is called only when parsing the literal `<all_urls>` (`url_pattern.cc` line 201), so `*://*/*` does not count. Experiment: with `host_permissions: ["http://localhost/*"]` the call failed with "Either the '<all_urls>' or 'activeTab' permission is required."; with `<all_urls>` it worked. [verified-src + verified-exp]
- `activeTab` is granted on action click, context menu click, command shortcut, or omnibox accept (docs), lasts until the user navigates to another origin or closes the tab, and is not granted by side-panel clicks (not listed). [verified-doc]
- **Rate limit.** `MAX_CAPTURE_VISIBLE_TAB_CALLS_PER_SECOND` is 2. Four calls in a burst: the first plus one succeeded, two rejected with "This request exceeds the MAX_CAPTURE_VISIBLE_TAB_CALLS_PER_SECOND quota." [verified-doc + verified-exp]
- **devicePixelRatio.** With `--force-device-scale-factor=2` and a 1200x1337 viewport, the PNG was 2400x2674: output is in device pixels, so crop rectangles from `getBoundingClientRect()` must be multiplied by `devicePixelRatio`, and scaling to the design's 1600 px maximum is the extension's job (OffscreenCanvas). [verified-exp]
- **What it captures.** The viewport only, not the full page. A cross-origin iframe (`127.0.0.1` inside `localhost`) was present in the pixels (checked a magenta pixel inside it). The page's own DOM is captured, so the overlay, pins and card appear in the image unless hidden first; the design wants the element outlined, which means drawing the outline in the canvas after capture or hiding everything but the outline. [verified-exp for the iframe; the overlay point is [inferred]]
- Restricted pages (chrome:, other extensions, data:, Web Store) are capturable only with `activeTab`; `file:` needs file access; policy-blocked hosts are refused. [verified-doc + verified-src]
- Capture is of the tab shown in that window, so it must be foreground, and an active tab being the extension page gets you that page, so the extension must not move focus before capturing. [inferred]

## Awkward for the design

1. **Screenshots need `<all_urls>` or an invocation.** The design's "ask Chrome for host permission once per new dev domain" does not cover `captureVisibleTab`. Pick from one of: (a) declare optional `<all_urls>` and request it once from the side panel (also removes per-domain prompts, but is the scariest warning, relevant to the public release); (b) use per-domain grants for injection and `activeTab` for screenshots, which only works when the user began the session with the toolbar button, a command or a context-menu item on that tab, and breaks after navigation to another origin. Needs a decision.
2. **No bridge-initiated permission prompt.** Claiming a new domain from the CLI cannot open the dialog. The flow must be badge, then side panel (or toolbar button click), then a gesture. The design already shows the grey `!`; it should add "Allow access" with the exact origins to be granted.
3. **Re-register on every install or update.** The "reload the extension" advice in the design wipes registrations; the worker has to rebuild them from the bridge on startup, and between reload and rebuild claimed pages are untouched.
4. **Badge reset is manual** (section 4).
5. **Gestures in the service worker are brittle.** Call `sidePanel.open` and `permissions.request` first thing in the handler; do not fetch the bridge first (inferred for short awaits; 1.5 s is verified refused).
6. **Existing tabs** when a claim starts are not injected; reload them or inject explicitly.
7. **Overlay shows up in screenshots** (section 5), and DPR scaling is manual.
8. **Service worker lifetime.** Learning claims "from the bridge" while the worker sleeps needs polling or a long-poll fetch plus `chrome.alarms`. Not researched here; see new questions.

## Method

Throwaway MV3 extension in the scratchpad (`ext-test/`: `sw.js`, `panel.html`, `cs.js`, `main.js`), loaded into Chrome for Testing 158 through agent-browser (dedicated session, persistent profile, `--force-device-scale-factor=2` for the DPR run), two static pages on loopback ports 5201/5202. Gestures were trusted clicks from CDP. Not exercised: the permission dialog, a native context menu, a real keyboard shortcut, packed-extension restarts. Chromium source read from `chromium.googlesource.com/chromium/src` `main`.
